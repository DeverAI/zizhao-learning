[P0-1] `BUSY never went high (low for Nms straight …)` 里的"连续低 Nms"从来没有被计量过 —— 那条判据用的是"距第一次低的时刻"，而日志文案、以及你在 §20.4 记为"我重算过"的那句第三方结论，都假定它是连续低。
  现象：
    一次刷新发出 `0x22=0xF7`+`0x20` 之后，若 BUSY 在毫秒尺度上翻动（高/低交替，任何周期 ≥2ms 都算），
    `epd_wait_busy_ms(…, require_high=true)` 会在 `el - seen_low >= 300` 时返回 false，
    调用方 `epd_driver.c:783-785` 打 `full update timed out`… 不，走的是另一条：打的是
    `BUSY never went high (low for 300ms straight, first_low=1ms, cap=8000ms)`，然后 `s_ready=false`。
    这句话有两个可证的假：①"never went high" —— 它其实高过很多次，只是每次都不满两拍；
    ②"low for 300ms **straight**" —— 这 300ms 里根本不是直低，`seen_low` 是"第一次低"的时间戳，
    此后任何一次单拍高都不会重置它（也没有任何变量在记"这一段低从何时开始"）。
    后果链（可证的部分）：一次**可能已经受理**的刷新被作废 → `s_ready=false` → `eink_display.c:318` 的
    `s_panel_ok = epd_ready()` 变 false → 监视任务 `eink_display.c:380-382` 打
    "面板应答但没刷上（帧缓冲或刷白这步没过，看上一行）… → 查内存"，把现场指向内存，
    而真正发生的是 BUSY 判据在翻转线上误判；下一轮 `epd_panel_init()` 第一件事是 `epd_reset()`
    （`:307`）⇒ 打断一次仍在进行的刷新，而 0x26 基准平面已经写进去了（`:769-770` 已过，`:772` 的
    s_cmd_dropped 门也过不了它，因为它不是 SPI 失败）。你在 `:773-775` 亲口写过这种后果：

      `:502` 是对的但引用可核性不成立（读者打开 `epd_driver.h:3` 指的那份会核不到 ⇒ P2-6 见下）。

[P2-6]（挂在冲突 4 上，仍按格式补一条）三处引用不带文件夹名，跨两份同名 `epaper_port.c` 时会指错文件。
  现象：`烧录须知.md:10`、`epd_driver.c:502`、`eink_display.c:324` 都写"官方 `epaper_port.c:182`/`EPD_Power_ON`"，
    而 `epd_driver.c:137`/`:139`/todo 第 62 条引的 `epaper_port.c:161/164/168/24-29` 是 **`01`** 的行号；
    同一份文件在 `08` 里整体 **+1 行**（`08:6` 多了一行 `#include "axp_prot.h"`）。
  证据：命令 `grep -rn 'EPD_Power_ON\|epaper_port.c' hardware/烧录须知.md hardware/zizhao-esp32s3/main/epd_driver.c hardware/zizhao-esp32s3/main/epd_driver.h hardware/zizhao-esp32s3/main/eink_display.c` →
      烧录须知.md:10 / epd_driver.c:137 / :139 / :502 / epd_driver.h:3 / eink_display.c:324
    命令 `ls -d */`（在 `C:\esp\vendor_demo\ESP32-S3_e-Paper-3.97\ESP-IDF`）显示 `01_…`~`08_…` 六份里
      有 6 个 `components/epaper_port/epaper_port.c` 副本（命令 `find /c/esp/vendor_demo -name epaper_port.c`）。
  为什么成立：你的规矩（`排查记录:976`）是"指向 IDF/第三方源码的引用保留行号"，而前提是那份文件唯一；
    这里"epaper_port.c:168"在两个目录下不是同一行，且 `EPD_Power_ON` 只在其中一个里存在。

[P2-7] `s_ready` / `s_bus_ok` 是普通 `static bool`，却被 `epd_pins_release_if_unverified()` **在锁外**读；同文件对同类标志（`s_cmd_dropped`）却写了 `volatile`，`s_probing` 写了 `atomic_bool`。口径不一致。
  现象：`eink_sleep()` 拿不到显示锁（`eink_display.c:516` 超时）才走 `epd_pins_release_if_unverified()`，
    此时另一个任务（`eink_display.c:354` 的监视任务，`xTaskCreate` 未绑核，见 `:406`）可能正持锁改
    `s_ready`/`s_bus_ok`/`s_spi`（`:763`、`:777`、`:785`、`:913`、`:925`）。而本函数在 `:992` 无条件读它们。
    写侧的唯一同步是互斥锁，读侧没有锁、也没有原子 ⇒ 这是一个形式上未同步的跨核读。
  证据：命令 `grep -n 'static.*s_ready\|static.*s_bus_ok\|static.*s_probing\|static.*s_cmd_dropped\|static spi_device_handle_t' epd_driver.c` →
      64:static bool s_bus_ok = false;
      69:static bool s_ready = false;
      76:static atomic_bool s_probing;
      80:static volatile bool s_cmd_dropped = false;
    命令 `grep -n '' epd_driver.c | sed -n '968,1002p'` → `:973`/`:977` 只原子地碰 `s_probing`，`:992` 读的是两个普通 bool
    命令 `grep -n 'xTaskCreate' eink_display.c` → `406: BaseType_t ok = xTaskCreate(panel_watch_task, "epd_watch", 6144, NULL, 1, NULL);`（未绑核）
    命令 `grep -n 'xSemaphoreTake\|xSemaphoreGive' eink_display.c` → `:354`（监视任务持锁）、`:516`（深睡侧 20s 超时）
  为什么**不**成立为缺陷（我给得出这个结论，因为我把坏交错逐个试了一遍）：
    要出事必须是"读侧看到 `s_ready==false` 而写侧仍在发 SPI"。写侧把 `s_ready` 清成 false 的三个点
    （`:763`/`:777`/`:785`）都在**该轮最后一次 SPI 写之后**（`:761` 返回即不再写；`:772` 之后只剩 `:781/:782` 两笔，
    `:785` 在 `:783` 的等待之后），所以"false 已可见 + 还在写"这个组合不存在；
    而 `s_ready==true` 期间读侧走 `:997-999` 第三条出口、根本不碰句柄（这正是 todo 第 61 条说的"挡住它的是条件不是令牌"）。
    剩下的是编译器把 `:992` 的读提到 `:977` 那次原子 exchange 之前 —— 我在 5.1.6/GCC13 的默认优化下构造不出
    可达的坏结果（`:975-983` 的循环体调用了外部函数 `vTaskDelay`，编译器不能跨越它缓存这两个全局）。
  最小修法（不改任何判据、纯口径统一）：`s_ready`/`s_bus_ok` 改成 `static volatile bool`（与 `:80` 同风格），
    并把上面那段"为什么坏交错不存在"的两行论证写进 `:959-966` 那块（现在那里只论证了"令牌够用"，
    没论证"锁外读普通 bool 够用"）。成本：无运行时开销（这两个标志每轮读几次）。
