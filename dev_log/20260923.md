### 同步这一件事的完整判据（三条 + 08:2x 复算追加的第 4 条；缺一条就不能说"同步好了"）

1. **载荷对不对**：163 只 / 2,915,500 B，来源 = 工作树（`git ls-files -c` ∪ `ls-files -o --exclude-standard`，都要 `-c core.quotePath=false`），减黑名单 3 只；
   并且**必测一只本轮已知 dirty 的文件**：`provision_ap.c` 工作树 **238 行** vs `git archive HEAD` **42 行** —— 这一条直接否掉了"用 HEAD 打包"。
2. **通道对不对**：`scp` 两侧 size+md5 逐字相同只证明**传输入**没错；坏的一面出现在解包 —— Windows 自带 bsdtar 对 GNU tar 的 UTF-8 文件名按 GBK 解码，
   `TAR_EXIT=1`、**157/163**（少的 6 只连报错都没被我看见，因为 stderr 被我 `2>$null` 吞了）。换成 python `zipfile`（bit 11 置位）+ `Expand-Archive` 才对。
3. **落点完整性**：**与顺序无关**的聚合哈希 —— 每只 `sha256(rel_path_utf8 + 文件字节)` → 163 个摘要排序 → 再 sha256，本地与远端同为
   `46d66077fc966e9b211e9d69ada215669994811df9d96ee510051d3216f3a37b`。中途试过"比路径序列的哈希"，两侧都没算错却不相等（PS 文化排序 vs python 码点排序）。
   **【08:2x 追加｜这条当时漏了定义，下一轮复算必撞】** 上面那句必须补三项才算可复算：`rel_path` **剥掉顶层目录 `zizhao_20260923/`**、
   排序后**用 `\n` 连接**、**排除包内 `SYNC_MANIFEST.txt`**。按此定义本机对留存 zip 重跑 ⇒ `files=163 / bytes=2,915,500 / 46d66077…` 逐字命中。
   未剥前缀得 `d65413c3…`、无连接符得 `e9d669dd…` ⇒ 都**不是**判据，别拿它们当"远端不对"的证据。
   另澄清一组两口径：**zip 实体 164 条目 / 2,923,852 B** 与 **被同步文件 163 只 / 2,915,500 B** 都对，差的就是那只清单（8,352 B）。
4. **本轮自己复算的意义**：②那三项定义不是从记忆里补的，是先算出不匹配、再回读**产生那个数的那条命令**（`ht305_agg.ps1` 仍在 `%TEMP%`）才拿到的。
