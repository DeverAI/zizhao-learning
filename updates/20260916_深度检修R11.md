## 一、本轮暴露的硬伤

T1–T5 与「时间/日期」相关（用户明确点名）；T6–T8 为链式检查后半段挖出。

### T1 · 全站没有日期时间显示（用户明确点名）

**现象**：顶栏只有「自招学习 + 用户名 + 退出」。日期、星期、时钟一概没有。
只有一个 `/api/system/health` 里带 `day_key`，前端从不读它。

**为什么是硬伤**：这套系统的所有业务都以「今天」为轴——今日素材、今日审核、
时间表当天、离线包 `day_key`。用户看不到今天是几号星期几，就无法判断
「这条素材是不是今天的」「时间表高亮的是不是我该看的」。日期不是装饰，是业务坐标。

**修**：
- `config.py` 新增唯一时间基准：`BEIJING_TZ` / `beijing_now()` / `beijing_now_iso()` / `beijing_weekday_cn()`
- 新增接口 `GET /api/system/time`（**免鉴权**，登录页也要能显示）：
  ```json
  {"ok":true,"day_key":"2026-09-16","date_cn":"2026年09月16日","weekday":"周三",
   "weekday_index":2,"hm":"04:23","hms":"04:23:55",
   "iso":"2026-09-16T04:23:55+08:00","unix":1789503835,"tz":"CST-8"}
  ```
- `index.html` 顶栏插入 `#clockHm` / `#clockDate`；`app.css` 加 `.top-clock` 等样式
- `app.js`：`startClock()` 每秒本地走时 + 每 10 分钟跟服务端校一次（`clockSkewMs` 纠偏），
  且在 `bootstrap()` **之前**启动——否则登录页看不到时间

### T2 · 首页「今天是几号」无处可看

主页只有一句「点组件进入」。**修**：主页标题下加当日日期行
（`2026年09月16日 周三`），并给 `.today-flag` 上强调色。

### T3 · 时间表不认「今天」

两个问题叠在一起：
1. 7 行星期全长得一样，看不出今天在哪
2. 星期下拉默认停在「周一」，跟今天无关

**修**：
- 今天那行加 `.is-today`（左侧强调色竖条 + 底色），并在星期旁挂「今天」标签
- 下拉默认选中今天
- **换算陷阱**：JS `getDay()` 周日=0，服务端 `weekday` 周一=0。
  直接比较会错一天，必须 `(d.getDay() + 6) % 7`。这条已写进测试断言。

### T4 · 板端日期恒为 UTC（会差一天）

`clock_sync.c` 里 `setenv("TZ","CST-8",1); tzset();` 只在 `clock_sync_sntp()` 内部调用。
但 `main.c` 里有两条 `localtime_r` 路径在 SNTP 之前/之外：

- `power_policy_should_sleep()` —— 关机判定
- `refresh_clock_page()` —— 时钟页显示

冷启动（SNTP 未走或失败）时 TZ 还是默认 UTC，北京时间 07:30 会算成前一天 23:30，
**日期直接错一天，关机窗口也会提前/推迟 8 小时**。

**修**：
- `clock_sync.c` 拆出 `clock_tz_init()`，`main.c` 在 Wi-Fi 之前就调用，保证任何
  `localtime_r` 都在正确时区下
- 新增 `clock_format_date_cn()`：输出「2026年09月16日 周三」，
  且 `tm_year < 120`（即 <2020，未校时）时返回「未校准（联网后自动对时）」，不再吐 1970
- `clock_format_hm()` 同样加未校时守卫，返回 `--:--`

### T5 · 校园网 SNTP 失败 → 日期全废，无兜底

`clock_sync_sntp()` 是唯一校时入口，失败只打个 log。校园网封 UDP 123 很常见，
一旦失败，整块板子的日期/关机窗口/离线 `day_key` 全部不可信。

**修**：新增 `clock_sync_http(server_url)`——调 `GET /api/system/time` 取 `unix`
（纯 `strstr` + `atol` 解析，不引 cJSON，与 `power_policy.c` 同风格），
含合理值域校验（2020–2065）挡脏数据。`main.c` 流程改为：

```
clock_tz_init()
  → clock_sync_sntp()            # UDP，先试
  → 失败则 clock_sync_http()      # HTTP 兜底，封 UDP 也能对时
  → 都失败则 settimeofday(clock_stash_load())   # NVS 上次时间，标注可能过期
```

并新增 `clock_stash_save/load`：每次校时成功把 epoch 写 NVS，重启后先有个不白页的起点。
主循环也改为「未校时期间持续刷屏」，一旦校时成功立刻把「未校准」换成真实日期。

### T6 · 计算器：中文幂静默算成错值（最严重的一条）

`二的一百次方` 走到降级正则后，`的`/`次方` 被剔掉，只剩 **`210`**。
`2**100` 与 `210` 差了 30 个数量级，**学生拿到的答案完全错，却没有任何报错**。

同类还有 `八分之三` → `83`（中文分数是**反着说**的：八分之三 = 3/8）。

**修**（`routers/english_tools.py`）：
- 新增 `_cn_num()`：中文数字 → 阿拉伯数字（零/〇/一/二/两/…/十百千万，含「一百零五」）
- 新增 `_cn_power_expr()`：`二的一百次方` → `2**100`，**确定性规则，不走模型**
- 新增 `_cn_arith_expr()`：`三除以八再乘一百` → `3/8*100`；`A分之B` → `(B/A)`
- `_CN_OP` 表**长词优先**，且把「百分之多少」「占几成」「是多少」等**问句词先删空**——
  否则 `三除以八再乘一百百分之多少` 会把尾巴变成 `*`，整句语法错
- 降级链收敛为：本地幂规则 → 模型算式 → 幂规则 → 中文算式规则 → 422
  （`2的10次方` 原本也会退化成 `210`，现在命中本地规则）

### T7 · 幂防护误杀合法题（`2**100` 被拒）

`agent_tools.py` 里 `MAX_POW_EXPONENT = 64` 是过时防护，
`2**100` 是初高中常见题，却被判「exponent too large」。
同时 `MAX_ABS_VALUE = 1e15` 过严——初中就会遇到 `2**100`、复利、阶乘的量级。

**真正的风险不是「指数大」，而是「嵌套幂」**：`9**9**9` 底数被反复放大成天文数字，
才是能把 CPU/内存打满的那种。单层 `2**100` 就是 1.27e30，Python 毫秒级算完。

**修**：改为**结果量级预判** `_pow_ok()`，用对数算量级不从真值构造：
```python
return e * math.log10(b) <= 308.0     # float 上限
```
`MAX_ABS_VALUE` 提到 `1e308`，`_guard` 加 `OverflowError` 兜底（超大 int 转 float 溢出 = 必然越界）。
实测：`2**100` = 1267650600228229401496703205376 ✓ / `2**1023` 通过 / `2**1024` 拒绝 /
`9**9**9` **0.0ms 拒绝**（对数预判，根本没构造数）。

### T8 · 审核字数在门槛上反复摩擦（1498 < 1500）

`_extend_body` 的目标是「刚好等于下限 `lo`」。免费模型输出长度天然抖动，
实测续写到 **1498 字**，离 `material_body_min_chars=1500` 差 2 字，
审核第 1 轮直接判「正文过短」——白烧 4 轮才放过。

**修**（`services/generator.py`）：目标改为 `int(lo * 1.1)`，留 10% 安全余量；
补不上去时写 `generator:extend_body_short` 到 `Err.log`，
否则下次只会看到「审核莫名 4 轮才过」而查不出原因。
